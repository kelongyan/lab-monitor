# 跨相机行人轨迹可视化演示 —— 方案分析

> 目的：在管理界面中呈现"同一行人跨越多路相机"的过程，作为能力一/能力二的直观演示
> 范围：仅需 2~3 个演示样例
> 结论日期：2026-09-15 · 代码基线 `ec6153d`

---

## 0. 实施结果（2026-09-15 已完成，本文档已从方案转为实施记录）

推荐方案（形态 B + C）已全部落地并上线：

| 交付项 | 位置 |

| 归并护栏 | `scripts/consolidate_identities.py`（见 §3.3） |

**已核对可用的演示样例**（均逐张目视确认各相机中确为同一人）：

| 样例 | 覆盖相机 | 视点数 | 说明 |
|---|---|---|---|
| **`5a7991c7`（推荐）** | `rnd_04` / `rnd_22` / `rnd_06` | 3 | 画面干净、含一个多视角窗口，最适合演示 |
| `d1742abb` | `rnd_04` / `rnd_22` / `rnd_06` / `rnd_21` | 3 | 4 路相机但 `rnd_21` 与 `rnd_22` 描述相同（同一视点） |
| `23c29863`（备选） | `rnd_05` / `reg_06` / `rnd_07` | 2 | `reg_06` 与 `rnd_07` 描述相同；`reg_06` 抓拍被烧录时间戳遮挡人体 |

三个身份的素材已确认**互不相同**（`videos_low/*.mp4` 的 md5 与实测时长均不同），
不存在"同一段素材当成两台相机"的情况。

**本次实施中踩到并修正的问题**（已写入代码注释与测试）：

1. **选样必须逐相机排序**。初版把全部候选按框面积全局排序再取前 N 行、然后分组，
   结果 `d1742abb` 跨 4 路却只出 2 路图 —— 远距离机位的小框被大框相机挤掉了。
   改为先取相机清单、再逐相机取最大框。
2. **`bbox_json` 位于处理帧 960×540 空间**，不是源片分辨率（实测依据：bbox 的
   `y2` 恒等于 `540.0`）。低清素材恰为 960×540，坐标可直接使用；测试用 480×270
   的合成素材验证等比换算确实生效。
3. **缓存侧车文件只存文件名**，绝对路径在回读时用当前目录重建 —— 否则换工作目录后
   旧相对路径失效（首次实现即踩到）。

## 1. 结论

**技术上可行，且已完成端到端验证；但不建议直接做"平面图轨迹"，应有条件地选择演示形态。**

实测验证结果（本次已完成）：

| 验证项 | 结果 |
|---|---|
| 轨迹接口 `/api/identities/{gid}/trajectory` | 已实现，返回 segments / path / 循环折叠信息 |
| 平面图接口 `/api/floorplan` | 已实现，返回底图与 22 路点位 |
| 从低清素材按 `video_ts` + `bbox` 裁出真人抓拍 | **可行**（已生成 `outputs/dev/demo_strips/`） |
| 抓图坐标系口径 | `bbox_json` 位于**处理帧** 960×540 空间，与低清素材尺寸一致，可直接使用 |
| 平面图坐标 `map_xy` | **全部为空** → 平面图轨迹当前无法绘制 |
| 相机序列质量 | **存在高频交替**（详见 §3.2） |

其中一项已产出的实证：`outputs/dev/demo_strips/d1742abb_strip.jpg`，从 4 路相机各取一帧真实抓拍并按相机名拼图，可直接看到同一名穿反光背心的工作人员出现在不同相机画面中。

生成脚本：`scripts/render_cross_camera_strip.py`（可复现，支持 `--list` 选样、`--report` 诊断）。

## 2. 三种可选演示形态

| 形态 | 呈现方式 | 依赖 | 说服力 | 成本 |
|---|---|---|---|---|
| **A · 平面图轨迹** | 楼层平面图上画出行走路线 + 播放头动画 | 需先标定相机点位 | 最强 | 高（需人工标点 + 序列清洗） |
| **B · 通行链时间轴** | 按时间列出经过的相机与时段，形成链路 | 无 | 中高 | 低 |
| **C · 跨相机抓拍序列** | 各路相机的真实抓拍并排对比 | 无 | **高（画面直观、无法质疑造假）** | **低（已验证）** |

**推荐 B + C 组合起步**，A 作为第二阶段增强。理由：C 的素材全部来自真实帧且带烧录的相机名与时间，是当前最能直接证明"跨相机同一人"的形态；而 A 依赖的标定与序列清洗均未完成，强行实施会先付出高成本、再暴露数据问题。

## 3. 三项前置阻塞

### 3.1 平面图坐标全为空（阻塞形态 A）

`config/camera_map.json` 中 22 条记录的 `map_xy` 均为 `null`，`facing_deg` / `fov_deg` 为默认值。因此 `trajectory` 接口返回的每个 segment 的 `map_xy` 都是 `null`，前端无法落点。

**已有的解决工具**：`outputs/dev/calibrate_floorplan.html`（底图 `outputs/dev/floorplan.png`，含四象限放大切片），在浏览器中点击即可落点并导出 `camera_map.json`。

**成本可控**：若只做 2~3 个演示，**只需标定这些演示涉及的相机，约 6~8 个点位**，而非全部 22 路。

### 3.2 相机序列为高频交替，不是行走路线（阻塞 A，且影响 B 的呈现）

实测相机切换序列：

| 身份 | 轨迹行数 | 相机数 | 相机切换次数 | 判定 |
|---|---|---|---|---|
| `d1742abb` | 5,316 | 4 | **1,863** | 高频交替 |
| `23c29863` | 140,453 | 3 | **14,684** | 高频交替 |
| `5a7991c7` | 1,506 | 3 | 125 | 高频交替 |

原始序列样例（`5a7991c7`，按时间排序后压缩相机切换）：

```
rnd_04  +0.0s → +132.7s      ← 一段正常的 132 秒停留
rnd_22  +132.9s              ← 此后在 rnd_04 / rnd_22 之间
rnd_04  +133.2s                 每 0.2~0.5 秒交替一次
rnd_22  +133.4s                 （video_ts 稳定在 14~15 秒）
rnd_04  +133.8s
...
```

**成因**：素材为循环播放的短片段，两条走廊相机的画面被并行处理，同一身份在两侧被交替确认，从而写入大量交替行。这不是人员实际往返。

**后果**：直接按 `path` 连折线，会得到一条在两个相机点位之间反复横跳的锯齿，**不仅无说服力，还会引出"轨迹为什么来回跑"的质疑**。

**处理方向**：在 `src/trajectory.py` 的停留段聚合之后增加一层"往返抖动合并"（合并间隔小于阈值的同相机段、剔除时长为 0 的段），或对演示限定较窄的时间窗并只取首次进入各相机的时段。

### 3.3 身份库退化，个别"跨相机身份"可能混人（影响全部形态）

当前 165 个身份中 62 个（37.8%）处于 9 个特征完全重复的组内，同时存在跨 22 路相机的污染身份。这意味着**被检索出的"同一人"未必真的是同一人**。

本次抓图过程中已观察到可疑迹象：一名持白色导盲杖的人员同时出现在 `d1742abb`（rnd_21 / rnd_22）与 `23c29863`（rnd_05）两个不同身份的轨迹中。在身份库未清理前，这一现象无法排除。

**结论**：演示样例必须**逐张目视核对**后才能使用。这既是质量要求，也是避免在评审现场被反问的必要措施。

#### 3.3.1 已实测：此库**无法用归并修复**（2026-09-15）

原计划是先跑身份归并清理重复注册。实测后**否决**了该操作：

| 归并阈值 | 候选身份对数 |
|---|---|
| 0.68（默认，与线上匹配一致） | 7,493 / 13,530 对（**55.4%**） |
| 0.95 | 7,276 |
| 0.99 | 7,179 |
| 0.999 | 7,171 |
| **1.0** | **6,340** |
| > 1.0 | 0 |

**阈值取 1.0 时仍有 6,340 组候选** —— 这说明大量不同身份的**中心化特征在数值上完全相同**，特征空间对多数身份已经退化。这种状态下任何阈值都会把整个库并成极少数身份，归并结果没有意义（"所有人都是同一个人"）。

成因量化：重复注册集中在**单路相机**——9 个重复组全部是相机内重复（`rnd_04`×8 组 / `reg_02`×1 / `rnd_06`×1），`rnd_04` 一路就占 113/165 个身份，而其源片只有 **20.04 秒**、循环播放，导致同一张人脸被反复注册。重复组只涉及 6/76 个跨相机身份。

**已采取的措施**：给 `scripts/consolidate_identities.py` 加上候选占比护栏（`_COLLAPSE_GUARD_RATIO = 5%`）与 `--force` 逃生阀 —— 默认执行会被拒绝并打印上述证据，避免误操作把库毁掉。生产库本次**未被改动**。

**正确修复路径**：重建身份库（见 `docs/TODO_2026-09-12_worklist.md` 项 1.5）并同时解决重复注册成因；判定滞后机制需要每臂 ≥30 分钟的长窗口对照实验，或跨相机人工标注集就位。这属于独立议题，不阻塞本次演示。


### 3.4 附：部分"跨相机"实为同一视角

`config/camera_map.json` 中存在描述完全相同的相机对：

- `rnd_21` 与 `rnd_22` 均为「L2高性能机房04通道西南向北」
- `reg_06` 与 `rnd_07` 均为「L2中间走廊西西向东」

实测 `d1742abb` 的 `rnd_21` 与 `rnd_22` 抓拍为**同一帧**（文件字节一致）。因此选样时应把这类相机对视为**一个视点**，否则"跨 4 路相机"实际只覆盖 3 个视点，且拼图中会出现重复画面。

## 4. 推荐实施步骤

**第一阶段（形态 C，成本最低，可最快看到效果）**

1. 清理身份库：`scripts/consolidate_identities.py --dry-run` 查看归并候选，确认后执行（脚本自动备份）
2. 用 `scripts/render_cross_camera_strip.py --list` 挑选 2~3 个候选身份，优先选择各相机均有完好正/侧身抓拍的样例
3. 用 `--gid` 生成对比图，**逐张目视核对**，剔除混人样例
4. 前端接入：在身份详情弹窗中新增一栏"跨相机抓拍"，直接调用已有的抓拍图资源（静态 JPG，不占用 MJPEG 连接）

**第二阶段（形态 B，与第一阶段可并行）**

5. 在身份详情中增加"通行链"列表：按时间顺序列出 `相机 / 描述 / 首次进入 / 末次离开 / 停留时长 / 命中帧数`，并对 0 秒段做合并后展示

**第三阶段（形态 A，需先补前置）**

6. 先按 §3.2 处理往返抖动，再标定演示涉及的 6~8 个相机点位（`outputs/dev/calibrate_floorplan.html`）
7. 前端在平面图上渲染 segments 与播放头

## 5. 工作量与风险

| 项 | 评估 |
|---|---|
| 抓拍序列（形态 C） | 生成脚本已完成，剩余为选样与目视核对，以及前端展示栏位 |
| 通行链（形态 B） | 数据已在接口中，主要是前端列表渲染 |
| 平面图轨迹（形态 A） | 需额外完成序列清洗 + 点位标定，工作量显著高于 B/C |
| **主要风险** | 身份库未清理时，演示样例可能混入他人；**必须目视核对**后再用于对外演示 |
| 次要风险 | 抓拍以背面/俯视为主，缺少正脸；建议选样时优先挑侧身或中距离样本 |

## 6. 结论

演示能力的**数据链路已打通并能产出真实证据**（抓拍序列已实证），建议先以"抓拍序列 + 通行链"两种形态交付 2~3 个样例——这两者不依赖平面图标定，且素材完全来自真实帧，可信度最高。

平面图轨迹虽然视觉效果最好，但其前置条件（点位标定、往返抖动清洗、身份库清理）尚未具备，建议作为第二阶段目标，**不宜在评审前赶工**。
